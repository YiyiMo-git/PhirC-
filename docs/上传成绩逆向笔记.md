# 成绩上传：逆向笔记（目标：让开源构建也能上传）

> 结论先行：**上传在开源构建里是死代码**，但**逆向出来是可行的**，因为官方客户端没被 strip，
> 编码器是可定位、可分析的真实函数。这份笔记记录已确认的事实、还缺什么、下一步怎么做。

## 1. 为什么开源构建传不了（已确认）

| 事实 | 出处 |
|---|---|
| `rated` 硬编码为 false | `phira/src/scene/song.rs`：`#[cfg(not(closed))] let rated = false;` |
| 于是每局都弹 `warn-unrated`（"本局成绩不计入排行"） | 同文件，`if !rated && can_rated && mode == GameMode::Normal` |
| 上传数据在引擎里构造 | `prpr/src/scene/game.rs` 的 `#[cfg(closed)]` 块：`record_data = Some(encode_record(self, player.id, *chart))` |
| `encode_record` 在仓库里**没有定义** | 全仓库搜索只找到那一处调用 |
| 闭源模块 | `prpr/src/scene/game.rs:114`：`#[cfg(closed)] mod inner;`（`inner.rs` 不在仓库里）|

上传接口本身是**开放可见**的（在 `phira/src/scene/song.rs` 里）：

```rust
Client::post("/play/upload", &Req {
    chart: i32,
    token: String,                      // = STANDARD.encode(record_data)
    chart_updated: Option<DateTime<Utc>>,
})
```

也就是说：**接口不需要逆向，缺的是 `record_data`（token）那个 blob 怎么生成**。

## 7. 第一轮反汇编结果（重要）

### 7.1 `resolve_data`（156 B）—— 结构已看清

```
sub sp …（栈帧）
bl  custom_dec@plt          ← 解密，参数是 (x0 = 输入指针, x8 = 输出槽)
ldr q0, [x20] / stp …       ← 把结果按 Rust 的 String/Vec 布局（ptr,len,cap 3 个字）搬走
bl  0x9643a4                ← 再走一步（压缩/解析之类）
失败路径：构造一个 40 字节的错误消息 + panic
```
⇒ 它就是「custom_dec + 后处理」的薄包装。**调用约定**：`custom_dec(x0=输入, x8=返回槽)`。

### 7.2 `custom_enc`（1884 B）—— **被混淆了**

开头就是典型的不透明常量 + 间接调用：

```asm
mov/movk ×4   → x24 = 0xddec255692d89ce9     ← 64 位不透明常量
adrp x8, 0x18c3000 ; ldr x8, [x8, #0x2a8]    ← 取全局指针
ldr  x8, [x8, x24]                           ← 用巨大偏移取数据
mov/movk ×4   → x10 = 0x779fe40f101c93b0
add  x8, x8, x10
blr  x8                                      ← 间接调用（真实目标运行时才算得出）
```
⇒ 直接读死代码没用，要动态跟或者把常量表解出来。**这是本次逆向最硬的一块。**

### 7.3 `encode_record`（6328 B / 1588 行）—— **没有混淆** ✅

统计：`blr` = 0、`br` = 0、`movk` = 0 —— 全是直接调用和普通常量。
反复引用 `0x18c3000` 段（全局表/重定位区）和 `0x275000` 段（常量与字符串）。

⇒ **记录的序列化部分是能读懂的**：它大概做三件事
1. 把成绩字段（chart id / player id / 分数 / 准度 / 判定计数 / 版本等）拼成一段内存
2. 调用 `custom_enc` 加密（唯一难读的部分）
3. 可能再叠一层压缩（官方 .so 里带 zstd）

### 7.4 结论：难度重新评估

| 部分 | 难度 | 说明 |
|---|---|---|
| 上传接口调用 | 无 | 开源树里就有（`/play/upload` + base64 token）|
| 记录序列化 | **中** | `encode_record` 未混淆，可读；1588 行要耐心读 |
| 加密（`custom_enc`/`custom_dec`） | **高** | 被混淆，需动态调试或解常量表 |
| 服务端额外校验 | **未知** | 只有真机实测才知道 |

**两条路，成本差很多：**

- **A. 抓包（快）**：在真机上用 mitmproxy 抓一次官方客户端的真实上传请求，
  拿到 token blob → 看它是不是 `zstd + 明文 protobuf`。
  如果是明文（只是 base64/压缩），**当天就能实现**，根本不用啃 `custom_enc`。
  需要你：手机、已登录账号、装信任证书、打一局官方谱面。
- **B. 纯静态逆向（慢、不确定）**：把 `custom_enc` 的混淆解开 + 读 1588 行
  `encode_record`。要几轮，且**如果密钥是运行时派生/从服务器拿的，静态根本拿不到**。

建议先做 A（成本低、结论明确）；A 抓到的 blob 也正好能验证 B 的成果。

| 指标 | 值 | 含义 |

### 8.4 下一步需要的数据（决定性）

**同一张谱面（46304）再上传 2–3 次，分数各不相同。** 理由：
1. 逐字节对比 → 直接看出**哪些字节编码分数/准度/判定数**（变的就是它们）
2. 两条等长数据**异或** → 若出现长串相同的值，就证明是"明文 ⊕ 固定 keystream"，
   可进一步推出 keystream；若异或结果仍高熵，则 keystream 与位置/时间相关
3. 再抓一条**不同谱面** → 定位 chart id 字段
4. 若能重打出一模一样的分数 → 可判断有没有 nonce/时间戳（相同输入是否产生相同输出）

⚠️ 新风险：若尾部确实是服务端校验用的 MAC/签名，那么**光会编码还不够**，
还要能算出 MAC —— 那需要密钥，静态逆向 `custom_enc` 就绕不过去了。
下一批样本能直接验证这一点（若两次上传的尾段呈现"整体高熵但长度固定"，
且头段呈现明显差分，就基本能确认是「混淆字段 + 独立 MAC」的结构）。

## 9. 静态逆向 `custom_enc`：混淆方案已解开

### 9.1 混淆手法（已破解并验证两次）

它的「不透明常量 + 巨型偏移」其实是**指针隐藏**，规则是：

```
真实地址 = 重定位表里的值 + 不透明常量   (按 2^64 回绕)
```

**验证 1**（GOT 取数）：
```
槽 0x18c32a8 的 R_AARCH64_RELATIVE addend = 0x2213daa96eb39567
混淆常量 x24                              = 0xddec255692d89ce9
相加（mod 2^64）                           = 0x00000000018c3250   ✓ 合法地址
```
**验证 2**（间接调用目标，槽的值是负数）：
```
槽 0x18c3250 的 addend = -0x779fe40f0f49d128 ≡ 0x88601bf0f0b62ed8
加上混淆增量 x10        = 0x779fe40f101c93b0
相加（回绕）            = 0x0000000000D2C288   ✓ 真实目标
```

⇒ 只要能从 `-R` 拿到槽的 addend，**任何一处隐藏调用/数据都能算出来**。
工具：`llvm-objdump -d`（反汇编）+ `llvm-objdump -R`（重定位），都在 NDK 里。

### 9.2 已解出的那个间接调用 = `Vec::resize`

`custom_enc` 全函数只有 **1 处 `blr`、0 处 `bl`**（477 行反汇编）。那个 blr 的目标 `0xD2C288`
反汇编出来是标准库辅助：

```
ldr x19, [x0, #0x10]     ; Vec 的 len
subs x20, x1, x19        ; 目标长度 - 当前长度
bl  memset@plt           ; 扩容后补零
strb w2, [x8]            ; 写入字节
str x1, [x0, #0x10]      ; 回写 len
```
⇒ 就是 `Vec::resize(len, byte)` 一类。**不是加密核心** —— 也就是说
**加密逻辑是内联在 `custom_enc` 的 477 行里的**，没有单独的核心函数可找。

### 9.3 观察：常量成族

x19/x21/x22/x23/x25/x26/x27/x28 的高 32 位全是 `0xffea5921`，
只有低 32 位不同 ⇒ 它们是**同一基准下的 8 个隐藏指针**（delta 形式）。
用 9.1 的方法逐个还原，就能把 477 行里 23 处寄存器偏移取数全部映射成
「哪次是 memcpy / memset / Vec 操作 / 真正的逻辑」，剩下的才是要读的算法本体。

### 9.4 下一步（按顺序）

1. 脚本化：把 `custom_enc` 里 23 处 `ldr xN,[xN,xN]` 的 (槽, 常量) 全部解出真实地址，
   逐个反汇编，标注成辅助函数还是逻辑 —— 把 477 行里"噪音"删掉
2. 精读剩下的真逻辑：目标是还原那个**非线性变换**（8.3 节证明它不是单纯异或）
3. 同时读 `encode_record`（1588 行、未混淆）确定**明文字段布局**
   （已知：chart=46304、chartUpdated、分数 9550/109839 —— 但分数在任何简单编码里都找不到，
   说明序列化本身也带变换）
4. 实现 + 真机对服务器验证

### 9.5 仍然未解的风险（不因上面的进展而消失）

- 若尾部 37 字节确实是对记录的 **MAC/签名**，则即使算法与布局全部还原，
  **仍需要密钥才能生成合法记录** —— 密钥可能是运行时派生、可能来自服务器。
- 服务端可能还有额外校验（版本、时间窗口）。

**结论：技术上已经"进了门"（混淆方案破解、工具链就位、噪音与逻辑可分离），
但"能不能真正上传"仍取决于密钥是否可从静态代码中取得。**

## 11. 间接表 dump 结果 ⇒ 这是**控制流平坦化 / VM 式分发**

用 `docs/rev/table.py`（遍历表内每个 8 字节槽，拿已知不透明常量族去解）dump
`0x18c2fe0`–`0x18c32c8`（93 个槽），发现槽值有决定性规律：

```
0x18c2fe0  0x6b14cc6877520839
0x18c2fe8  0x6b14cc6877520a2d
0x18c2ff0  0x6b14cc6877521aa5
0x18c3000  0x6b14cc6877520c4d
...（93 个槽的高 48 位完全一致：0x6b14cc687752）
```

⇒ 整张表是**用同一个常量混淆过的指针表**，而且**差值被保留**：
`值ᵢ − 值ⱼ = 真实ᵢ − 真实ⱼ`。把低位排开：

```
0471 04bd 05c9 06d5 07ed 0865 09bd 09d5 0a2d 0a2d 0a61 0b69 0bc9 0c05 0c29
0c4d 0c71 0d8d 0da5 0f29 0f71 0f9d 0fc9 13dd 140d 14a1 15b1 15dd 1649
1a9d 1a9d 1aa5 1aa5 1aa5 1aad 1aad 1aad 1b01 1b49 1c1d
```

**跨度约 6 KB、93 个入口、间隔全是 4 的倍数** ⇒ 典型特征：
**93 个小 stub（每个约 8–16 条指令）挤在一段 6KB 代码里，由这张表间接分发** ——
也就是 OLLVM 的**控制流平坦化（或自研 VM 分发）**。

### 11.1 这对工作量的影响（重要）

之前以为"混淆只是几处隐藏调用"，现在看是**函数逻辑被拆成 ~93 个 handler 并表驱动分发**。
要静态还原算法，需要：
1. 先解出混淆密钥（用"差值保留"这个性质 + 定位那 6KB 的 handler 区）
2. 再逐个读 93 个 handler，重建分发的状态机（这已接近"逆向一个自研 VM"）

工作量从"读 477 行"变成"**逆向一个 VM + 93 个 handler**"，而且 `encode_record`
（1588 行）里同样有 46 处走这张表 ⇒ 两个函数都受影响。

### 11.2 这条路的现实评估

- **仍然可行但成本大幅上升**；静态路线的下一小步是明确的：
  解出表的混淆密钥 → dump 那 6KB handler 区 → 看 handler 的形态（是否真有 VM 字节流）。
- **更务实的替代**：动态分析（root 的安卓设备/模拟器上跑 Frida，或 Windows 版用调试器）
  直接 hook `encode_record`/`custom_enc` 的入参出参，跳过静态还原 ——
  但需要一个能跑起来并被调试的环境（Windows 版最容易，因为本机就能跑）。
- 无论哪条路，**"尾部 37 字节是不是 MAC、密钥从哪来"这个根本问题依然悬着**。

### 11.3 给决策用的一句话

现状：混淆比预期重（VM 式），静态还原是"能走但很贵"的路；
动态分析（本机 Windows 版 + 调试器 hook）可能几小时内就能拿到"输入→输出"的映射，
但**只能得到行为，不一定能得到可复现的算法**（若密钥随机/来自服务器则仍然没戏）。

## 13. 混淆机制**完全解开**：两级加密指针表（手工 GOT）

## 15. 编码链路完全闭环：raw deflate + HMAC + 无密钥 custom_enc（2026-09-19）

这一节推翻了之前两个判断，并给出了可复现的完整链路。

### 15.1 抓包 token 不是"无压缩弱混淆"，而是 raw deflate

之前观察的是 **压缩后的字节**，所以看到"无魔数、高熵、尾部 37 字节高熵"。
实际用 Python：

```python
zlib.decompress(token_bytes, -15)   # raw deflate，无 zlib/gzip 头
```

133 字节 token 稳定解出 **128 字节**。

### 15.2 128 字节 = 96 字节 custom_enc 输出 + 32 字节 HMAC-SHA256

```text
96 字节  custom_enc(record_92B + 0x0c padding)
32 字节  HMAC-SHA256(key, 96 字节 custom_enc 输出)
```

已用两个真实样本验证：尾部 32 字节与 Python `hmac.new(...)` 完全一致。

### 15.3 `custom_enc` 已完整还原：无密钥确定变换

伪代码：

```rust
fn custom_enc(data: Vec<u8>) -> Vec<u8> {
    let n = data.len();
    let pad = n & 0xf;
    let new_len = (n & !0xf) + 0x10;
    data.resize(new_len, pad);

    for block in data.chunks_mut(16) {
        zeta_transform(block);   // 4 维子集和
        bitrev4_permute(block);  // 4-bit 位反转
    }
    data
}
```

其中 `zeta_transform`：

```text
out[i] = Σ_{j ⊆ i} in[j] mod 256, i = 0..15
```

没有运行时密钥，没有服务器下发密钥；静态可复现。

### 15.4 HMAC key 是静态 ASCII 常量

libphira.so 中 26 字节混淆数据经固定 XOR 解开后为：

```text
KTCfLeu6d6gq957WOEyj-light
```

随后标准 `HMAC-SHA256(key, custom_enc_output)` 即可得到尾部 32 字节。
这排除了之前最大的风险："尾部 MAC 密钥来自运行时/服务器"。

## 19. offset 21..23：写入点已定位、公式已确定，但语义仍未闭合（本轮）

本轮把 `encode_record`（0xd24860，1588 行）里**写 offset 21..23 的那三条指令**精确找到了。
不是位打包的"猜"，是直接读代码。

### 19.1 写入点与公式（来自反汇编，非推测）

```asm
d252fc: ldur w9,  [x29, #-0x8]      ; A
d25304: and  w10, w26, #0xfffffffe  ; B & ~1
d2530c: and  w11, w19, #0xfe        ; C & 0xfe
d25310: and  w9,  w9,  #0xfffffffe  ; A & ~1
d25318: orr  w9,  w9,  w22          ; | flagA
d2531c: orr  w10, w10, w12          ; | flagB
d25320: strb w9,  [x8]              ; -> offset 21
d25324: orr  w9,  w11, w23          ; | flagC
d25328: strb w10, [x8, #0x1]        ; -> offset 22
d2532c: strb w9,  [x8, #0x2]        ; -> offset 23
d2533c: add  x8,  x8, #0x3          ; Vec len += 3（确认就是 21..23）
```

即：

```text
byte21 = (A & ~1) | flagA
byte22 = (B & ~1) | flagB
byte23 = (C & 0xfe) | flagC
```

三个 flag 都是**运行时算出来的布尔**（不是 A/B/C 的最低位）：

- `flagA` = `w22`，来自 `0xd251b4: mov w22, w21`（比较链结果）
- `flagB` = `[sp+0x4]`，来自 `0xd24fe0..0xd25014` 一串布尔混淆（输入是 `f32 [scene+0x29c]`，
  经 `fcvtzu …, #0xe` 定点化后与 `0x4000 / 0xffffffffffffbfff` 做位运算）
- `flagC` = `0xd25210: cmp w27, w23` -> `cset eq` -> `bic` 取反 -> `mov w23, w0`

### 19.3 关键观察（决定后续路线）

1. **18/18 个 bit0 全为 0** ⇒ 三个布尔 flag 在这 6 局里全部为 false。
   （若这三个字节是纯数据而非 `&~1|flag`，18 位全偶的概率是 2^-18 ≈ 4e-6 ⇒ 公式可信。）
2. **A/B/C 来自同一个全局对象**：三个读取点分别是
   `0xd24f54 ldr w8,[x23,x8,lsl#2]`、`0xd25074 ldr w26,[x24,x8,lsl#2]`、`0xd25298 ldr w19,[x25,x8,lsl#2]`，
   而 x23/x24/x25 都来自 `bl 0xe788fc`，随后 `ldr x,[x0,#0x110]` 取"游标"、`str x,[x0,#0x110]` 游标 +1。
   对象形状：`[+0x00]=引用计数`、`[+0x10 .. +0x110]=64 个 u32`、`[+0x110]=游标`。
3. `0xe788fc`（`rev/hidden_e788fc.asm` 已 dump：OnceCell + 引用计数自增）**在整个 .so 只有 7 处引用**
   （0x81d7f8 / 0x84a8d8 / 0xb18aa0 / 0xb18b9c / d24e6c / d25018 / d2523c），
   其中 3 处就在 `encode_record` 内 ⇒ 这是**成绩编码专用对象**，不是通用混淆基础设施。
4. **决定性反例**：#3 与 #5 是几乎相同的两局（同谱面、同 n=205、P 175 vs 176、G 都是 3、
   mc 都是 59、var 0.008983 vs 0.008319），但字节差别巨大（196,198,60 vs 194,220,254）。
   ⇒ 这三个值与"成绩表现"不成比例相关，不像 early/late 这类小计数。
   同时 #3–#6 的 byte21 却相对稳定（196/180/194/200）⇒ 更像**与执行路径/控制流相关**的量。

### 19.4 本轮已排除（不要重走）

- ❌ **线性拟合**：假设 `v = a*P+b*G+c*B+d*M+e*mc+f*n+g (mod 256 或 mod 128)`，
  系数遍历 ±4，对 6 个样本三个字节位置**全部落空**。脚本：`docs/rev/fit_flags.py`。
- ❌ 不是 `early/late` 的直接序列化（#4 的 byte22=10 恰好等于实测 early=10，但 #3/#5 反例否决）。
- ❌ 早先笔记把 `0xd25028 mov w10, #0xd8` 当成"offset 28 常量"的锚点是**误判**：
  那处 `0xd8` 是混淆分支的偏移选择器（`csel x9, x10, x9, hi`），不是写进记录的常量。

**两条记录的前 33 字节只在 offset 21..23 不同**，其余（version / player id / chart id / variance /
u32@17 / u32@24 / 0xd8 / …）逐字节完全一致。

### 21.1 由这个数据点能推出什么

- 这两局是同一张谱面、同一账号、同样的 `counts=[0,0,0,205]`、`max_combo=0`、
  `num_of_notes=205`、**variance 都是精确的 0.0625**（= 0.25²，说明 Miss 的合成 diff 都是 ±0.25s）。
- 在这种"已记录统计量完全一致"的前提下，`c8 9a c6` 与 `32 dc 16` 仍然完全不同
  ⇒ **offset 21..23 不是"记录里已有的那些统计量"的确定性函数**。
- 结合 §19.3 的反例（#3 vs #5）可以确定：它们要么来自**没有进记录的量**
  （early/late 的符号分布、hist、原始 diff 序列），要么就是**非语义的**（§19.6 的两种解释之一）。
- ⚠️ 但要注意一个仍然成立的可能性：Miss 的 diff 符号是可变的（variance 一样但符号可以不同），
  所以"early/late 计数"仍然没被这个数据点排除 —— 它恰好也解释了 #6/#7 的差异。

### 21.2 对服务端探针的推论（重要）

两局在"除 21..23 外完全相同"的情况下**都被服务端接受**了。这说明：

> 无论服务端怎么处理这三个字节，它**不可能把它们与记录里其余字段做一致性校验**
> （否则 #6/#7 必然有一局通过、一局被拒）。

因此用 `variant=zero` 重传被接受的概率很高。探针仍然值得跑，因为还能顺便证明
"自制记录 + 已登录账号"这条链路本身能被服务端接受 —— 那是后面 Rust 实现的前提。

### 22.2 offset 9..16 f64 = variance：语义与算法**完全确定**

`prpr/src/judge.rs:898-908` 给出了 `commit` 收到的 `diff` 到底是什麼：

```rust
let synthetic = matches!(judgement, Judgement::Miss)
             || matches!(note.kind, NoteKind::Drag | NoteKind::Flick);
let timing = (!synthetic).then(|| (diff.unwrap_or(t) - note.time) / spd);
self.commit(t, judgement, line_id as _, id,
            timing.unwrap_or(if matches!(judgement, Judgement::Miss) { 0.25 } else { 0. }),
            timing);
```

所以每次判定进入 `JudgeInner::commit(what, diff)` 的 `diff` 是：

| 情况 | diff |
|---|---|
| Miss | **0.25**（合成值，精确常量） |
| Drag / Flick 音符（任意判定） | **0.0**（合成值） |
| Hold 自动 Perfect（`judge.rs:1012`） | **0.0** |
| 其它（真实计时） | `(命中时刻 - 音符时刻) / speed` |

而 offset 9..16 写的是（反汇编 `0xd24c48 / 0xd24c5c / 0xd24dc8` 确认）：

```text
variance = [scene+0xdc0] / (f64)[scene+0xdb0] = Σ diff² / count
```

### 22.3 模型对 7 个真实样本全部成立

4 个全 Miss 的样本（#6/#7/#8/#9）variance **精确等于 0.0625 = 0.25²** —— 这是"Miss 的
diff 恰好是 0.25"的直接证据，也顺带证明用的不是 histogram 反推（hist 半宽只有 200ms，
不可能给出 250ms 的量级）。

对其余样本，`Σ = variance × n` 减去 `M × 0.0625` 之后剩下的平方和，反推出来的
**真实计时标准差全在 27–70 ms**（合理人类值），且没有负数：


### 22.4 实现要点（照着这个写就不会错）

1. 在**开源版 `JudgeInner`** 里加两个累加器，在 `commit(what, diff)` 里更新：

   ```rust
   self.diff_sum_sq += diff * diff;
   self.diff_count += 1;
   ```

   `reset()` 里一起清零；`variance() = diff_sum_sq / diff_count as f64`。
   **必须在 `commit` 里累加**（而不是自己另算），只有这样 Drag/Flick/Hold 的合成 0.0
   才会被算进分母，与官方一致。
2. record 里 `num_of_notes` 与 variance 的分母在完整一局里是同一个数（每张谱的每个音符判定一次），
   但**分母用 `diff_count` 更保险**（练歌模式 `advance_to` 会跳过音符造成两者不等）。
3. offset 21..23 填 `00 00 00`。
4. offset 28/82/83 = `0xd8 / 0x74 / 0xd2` 硬编码（原始来源是全局 atomic，无法静态读取，
   但 9 个样本恒定）。
5. deflate 用 **level 0**（`Compression::none()`），保证与官方字节一致。

2. **`sync_docs.py`**：`docs/rev/` 整目录、文件名含「成绩/上传/逆向/抓包」、
   正文含敏感串的文档一律**不复制**（实测拦下 22 个）。
3. **`verify_new_repo.py`**：补上退出码（原来只打印不报错）+
   远端 `docs/` 白名单校验 + 新增文档加入 `MUST_BE_GONE`。

**实测**：正常源 → 通过、提交成功、`docs/` 正好三个白名单文件；
在源码里种一个含密钥的 `leak_probe.txt` → **拦住、exit 1、不留 `.git`**。

⚠️ **不要把裸 `encode_record` 加进 `FORBIDDEN`。** 上游自己的
`prpr/src/scene/game.rs` 与 `phira/src/scene/song.rs` 在 `#[cfg(closed)]`
里就有这个调用（闭源构建用，`aa14c13` 基线里已经存在，干净仓库里也有），
加了会每次都误报，门禁就废了。要盯的是**我们自己的**特征：
密钥串、`custom_enc`、`diff_sum_sq`、`HMAC_KEY`、`crate::record::encode_record`。

**发布流程（更新）**：
```
python rev\build_clean.py       # 提交前扫描，命中会拒绝提交并删 .git
python rev\verify_new_repo.py   # 校验远端；有退出码，非 0 就别交付
```
