## 附：上下文卫生 + 本次断点（**新会话务必先读这一段**）

### 为什么上一个会话会爆
报错是 `880319 in the messages, 256000 in the completion`，合计超过 1,048,576 上限。
**完成预留 256k 本身就占掉四分之一窗口**，剩下的给消息。加上本项目要读大量反汇编，
很容易撞线。对策：

- **反汇编/长输出一律写文件**（`rev/` 或 `docs/rev/`），**对话里只贴 ≤30 行的摘要**
- **每次只解决一个具体问题**（一个字段 / 一次验证），做完立刻把结论追加进
  `docs/上传成绩逆向笔记.md` —— 那份笔记就是外置记忆，会话炸了也不会丢
- 大文件先用 `Select-String` / 脚本过滤，**不要整份读进对话**
- 需要看长输出时，先想"我真正要判断的是什么"，只打印那几行

### 当前断点（从这里继续，不要重新调查）

**已完成并交叉验证**
- `custom_enc` = 无密钥确定变换：16 字节对齐填充（填充字节 = `len & 0xf`）→
  每块 4 维子集和变换 → 4-bit 位反转置换
- 最外层 = **raw deflate**（无 zlib/gzip 头，`zlib -15`）；133 → 128 字节
- 128 = 96（custom_enc 输出）+ 32（**HMAC-SHA256**，密钥为静态常量
  `KTCfLeu6d6gq957WOEyj-light` 经固定 XOR 还原，消息 = 那 96 字节）；两样本均逐字节匹配
- 92 字节明文布局（两样本完全对上）：
  `0` 版本=3 ｜ `1..4` player id (LE) ｜ `5..8` chart id (BE) ｜ `9..16` f64（未定）
  ｜ `17..20` u32 ｜ `21..23` 3 字节位打包（未定）｜ `24..27` 零值/占位 ｜ `28` 0xd8
  ｜ `29..32` **max_combo** ｜ `33..36` **counts[0] Perfect** ｜ `37..40` **counts[1] Good**
  ｜ `41..44` **counts[2] Bad** ｜ `45..48` **counts[3] Miss** ｜ `49` **speed×100**
  ｜ `50..81` **SHA-256(官方 chart 文件原始字节)** ｜ `82` 0x74 ｜ `83` 0xd2
  ｜ `84..87` **num_of_notes** ｜ `88..91` 0 ｜ `92..95` 0x0c 填充
- 两样本用 `prpr/src/core/judge.rs` 的精确公式反算，分数 9550 / 109839 **都对上** ✓

**只剩两个字段**
1. `offset 9..16` 的 f64（疑似 std / 平均判定偏差）
   → **不要填 0 试**：这类统计量最可能被反作弊看，填 0 比"值不精确"危险得多
2. `offset 21..23` 的三个标志字节（两样本 `ae ae 00` / `5e 6a aa`）
   → 两样本不同 ⇒ 不只是 `full_combo`，还打包了随成绩变化的小计数

**下一步（按优先级）**
1. 读 **`prpr/src/core/judge.rs`**（开源）里的 early / late / 小计数 / full_combo / AP 判定，
   再用两样本的 P/G/B/M **穷举 3 字节位打包组合**，对上就收工（半小时量级，失败就停）
2. f64 转**动态**：本机已有官方 PC 客户端（`rev\phira-pc\phira-main.exe`），
   跑一局 dump 真实 `early/late/std/hist/full_combo` —— **一次同时钉死两个字段**，
   而且拿到的真实值正好可以作为第一次实现试验的输入（服务端看到的统计才合理）
3. 两个字段闭环后再写实现：Rust 版 `custom_enc` + `HMAC-SHA256(静态密钥, 96B)` + `raw deflate`
   → 小号真机验证

**注意**：`chart hash` 用的是**官方 chart 文件的原始字节**做 SHA-256，
不要在实现里用"解析后重新序列化"的结果，否则服务端会判谱面不匹配而拒绝。
